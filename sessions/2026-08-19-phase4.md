# Session 2026-08-19 — Phase 4 EC Firmware RE + Phase 5 Recommendations

## Phase 4 — What we did

### 1. EC.bin format analysis (the hard part)

Confirmed the EC firmware is **plaintext** (not encrypted):

* The PKCS#7 wrapper is `signedData` (OID 1.2.840.113549.1.7.2), not
  `envelopedData` — so it's a signature, not encryption.
* The payload inside is 1.69 MB of plaintext ARM Cortex-M code.
* SHA256: `352a206d25f9d964dd83946126d5c7ba968f31944bbddb569cd183272c9a471a`.

**Architecture:** NXP LPC54S001J (Cortex-M4, 360 KB SRAM).
* Vector table at image offset `0x66C`:
  * Initial SP: `0x30080000` (256 KB SRAM at `0x30000000`)
  * Reset: `0x100F1E09` (Thumb)
  * HardFault: `0x1008CBE9`
* Firmware runs at `0x10000000` base.

**Container format (XLFF + MSS1/SAML):**
* `0x0000–0x077F`: XLFF header + PKCS#7 cert chain
* `0x0780`: `MSS1` marker
* `0x0790`: `SAML` marker
* `0x0900–0xCF417`: Image A chunks (40,294 chunks × 21 bytes)
* `0xCF438–0x19DD95`: Image B chunks (same 40,294 chunks, redundant copy)
* `0x19DDA0+`: trailing signature

**Chunk format:**
```
struct chunk {
    u32 offset;    // destination offset in image
    u8  len;       // = 16
    u8  payload[16];
};
```

### 2. Proper image extraction

* Initial extraction (`image1.bin`, 524,304 bytes) was **truncated**.
* Correct extraction: 40,294 chunks × 16 bytes = 644,720 bytes.
* Saved as `image_full.bin` (the proper one).
* Non-`0xFF` data ends at offset `0x767D0` (~484 KB).
* Code at addresses `0x100F1E09` etc. is **NOT** in the chunk payload —
  the chunks only contain the metadata layer (vector table, function
  pointer tables, config tables, strings). The actual machine code
  lives in a separate code region of the flash that this extraction
  does not cover.

### 3. SAM command dispatch table

Located a **SAM command dispatch table** at image offset `0xAAE0`–`0xABBC`.
49 entries, 12 bytes each:
```
struct sam_dispatch_entry {
    u32 fn;       // handler function (0x10xxxxxx)
    u32 tc_flag;  // (flags << 24) | target_category
    u32 cid;      // command_id
};
```

`flags`: `0x00` = NOTIF, `0x40` = GET, `0x80` = SET, `0xC0` = unknown.

**Dispatch map:**

| TC | Name | CIDs | Dir | Handlers |
|---|---|---|---|---|
| 0x00 | (untyped) | 0x00 | NOTIF | `0x100B41E2` |
| 0x01 | SAM | 0x00..0x11 | mixed | generic `0x100ABA52` + 4 specialized |
| 0x02 | BAT | 0x03, 0x06, 0x08, 0x0C, 0x0D, 0x0E, 0x0F, 0x12 | mixed | `0x100ABF1A`, `0x100B8682`, `0x100B9A92`, `0x100AF50A`, `0x100B1BA6`, generic |
| 0x03 | TMP | 0x00 NOTIF, 0x01/0x02/0x09 SET | mixed | `0x100ABA52`, `0x100ABC66`, `0x100ABF1A`, `0x100AC03E`, `0x100B1BA6`, `0x100AED9E`, `0x100AF50A`, `0x100B41E2` |
| **0x04** | **PMC** | **0x0A SET** | mixed | `0x100ABC66` |
| 0x05 | FAN | 0x00 NOTIF | NOTIF | `0x1008A2B8`, `0x100AC03E`, `0x100B1BA6`, `0x100B5F56` |

**Key finding:** TC `0x04` PMC has a SET command at CID `0x0A` (handler
`0x100ABC66`) — **the most likely candidate for the PCIe / power-limit
SET command** that has no Linux kernel client.

### 4. Other findings

* **90 function pointer tables** total in the image, the largest being
  an 89-entry table at `0x76658` (not decoded — different entry format,
  likely a TC-mask-based SAM registration table).
* **GPU power profiles** at `0x8520`–`0x8760` — 14 named profiles
  (Nominal/Quiet/Perf/Max/Gaming/Mixed_Reality/Kiosk × iGPU/dGPU),
  32 bytes per entry with name + freq/voltage/power-limit data.
* **Thermal sensors:** `BATT1_T`, `TP_TMP`, `I_RTS1`–`I_RTS6`,
  `I_RTS_TP`, `I_RTS_CRIT`, `I_VTS1`/`I_VTS2`, `U3901`–`U3904`,
  `DGPU TEMP (U8302)`. Trip points in 0.01 K.
* **Surflink (SSH) pins:** `SAM_SWD_CLK/DIO/SWO`, `SAM_RESET_N`,
  `SAM_PCH`, plus trackpad `I²C` pins. Explains why the trackpad works
  even in low-power states.
* **Subsystem notifiers:** Dispatcher, MagDirSample, MagDegaussing,
  Sensor Power, SOC_GEN, Typec Generic, ACS_CALIBRATION (factory cal).

### 5. The big limitation

The function bodies (code) at addresses `0x100xxxxx` are **not in the
chunk payload**. The chunks only contain metadata. The actual ARM
machine code lives in a separate code region of the flash that this
extraction does not cover. So we cannot disassemble the SAM handler
functions to see what they actually do.

To go further, we would need either:
1. A full flash dump (not just the chunks)
2. A different firmware extraction method that captures the code region
3. Update the EC and re-extract (but that's the "brick risk" path)

# Session 2026-08-19 — Phase 3 PCIe and Fan Findings

## What we did

### 1. .sys file static analysis (3 of 8 drivers)
- **SurfaceAcpiPlatformExtensionDriver.sys** (MSHW0299, boot-start PEP):
  - Loads the DMF AcpiPepDevice module
  - Acts as the AMDI PEP dispatcher for the kernel
  - **No direct PCIe code** — it dispatches to other modules
  - Identifies platform via `Surface Laptop` / `Surface Pro` strings
- **SurfaceIntegrationDriver.sys** (MSHW0360):
  - Loads `Surface.Power.Policy.Defaults.ppkg`
  - Defines SMF clients: `Surface SMF Display Client`, `Surface SMF Fan Client`,
    `Surface SMF IHV CPU Client`, `Surface SMF System Client`,
    `Surface SMF Thermal Client`, `Surface SMF Vpu Client`
  - `\Registry\Machine\System\CurrentControlSet\Control\PnP\Pci` — references
    the PCI subsystem but only for enumeration, not control
- **SurfaceSmfClient.sys**:
  - Multiple SMF channel clients
  - **6 fan SAM commands** that Linux doesn't implement:
    `SmfFanSetProfile`, `SmfFanMinRpm`, `SmfFanSetActiveSones`,
    `SmfFanSetMaxSones`, `SmfFanSetMcuMaxSones`, `SmfFanCsRequest`
  - `SmfFanInterface_ChannelUpdate.SplLimitRequested` mentions SPL
    (Sound Pressure Level) — implicates acoustic limits

### 2. ACPI table decompile
- `acpidump` → `acpixtract` → `iasl -d` on all 28 SSDTs + DSDT
- Found the **dGPU `_DSM`** at `\_SB.PC00.VMD0.NVDR`:
  - UUID: `a3316317-e8b6-4adf-96e8-94d94a51a38e`
  - Returns a 5-element Package: DPM0(u16), DPM1(u16), DPM2(u32), DPM3(u64), DPM4(u64)
  - `DPM3` = `PMSA` (dGPU power state address)
  - `DPM4` = `PMRL` (dGPU power reference)
  - All three are in platform NVS (SystemMemory 0x3DB5A018, size 0x037A)
  - **EC writes these fields; ACPI/Windows only reads them**
- 0 explicit link-speed controls (`LnkCtl2`, `TargetLinkSpeed`, etc.)
- 0 `_DSM` cases for `LnkCtl2` retrain

## Key findings

### Smokking gun: link is "downgraded" by hardware
The kernel's AER code marks the link as **"downgraded"** because:
- Both endpoints advertise Gen 4 (`LnkCtl2: Target Link Speed: 16GT/s`)
- Both endpoints completed equalization
- The actual link speed is 2.5GT/s
- **No errors, no retries** — the link is *stable* at Gen 1

This is the textbook signature of an **EC-supplied link speed cap** that
the BIOS reads and applies during early init. The EC maintains the cap
across warm reboots, so each boot starts at Gen 1 and the link-trainer
retrains at Gen 4 attempt but EC forces fallback.

### The dGPU `_DSM` is for power telemetry, not link control
The Surface dGPU `_DSM` returns a power state Package, not a link speed
control. Windows uses this to feed NVIDIA's Optimus power management.
**The actual link speed control is below the OS level** — likely in the
EC firmware's link-training policy.

### The Linux kernel has no SAM path for PCIe link speed
- `surface_hotplug.ko` has 0 SSAM symbols
- `surface_aggregator_cdev` exposes all 38 TCs, but no driver polls
  PCIe-related ones
- The cdev probe tool (validated) could discover a hidden TC, but the
  Phase 2 risk register flags this as **high risk** for TCs we don't
  understand

### EC firmware gap
- Running: **12.201.139**
- MSI ships: **13.101.139**
- Newer EC could have different link-training policy
- **Updating EC FW is out of scope** for this project

## What the SmfClient tells us about other SAM commands

The SmfClient has trace strings for SAM commands the kernel doesn't
expose. Strong hints at undiscovered CIDs:

| Trace string | Likely TC/CID |
|--------------|---------------|
| `SmfFanSetProfileSamCommand` | (FAN, 0x0e, 1) — known |
| `SmfFanMinRpmSamCommand` | unknown |
| `SmfFanSetActiveSonesSamCommand` | unknown |
| `SmfFanSetMaxSonesSamCommand` | unknown |
| `SmfFanSetMcuMaxSonesSamCommand` | unknown |
| `SmfFanCsRequestSamCommand` | unknown |
| `SmfFanSplLimitSamCommand` | unknown |

The `Smf_Channel` enums are abstract — the SAM command numbers are
discovered by tracing the function tables, which required manual RE
of the SmfClient. **We don't have those numbers yet**.

## Recommended next action

Phase 5 recommendations should include:

1. **The PCIe Gen 1 x8 problem is hardware-EC-controlled**, not OS.
   Anyone wanting to fix it needs to either:
   - Update EC FW (risk: bricking the EC)
   - Modify the LnkCtl2 register after boot via `setpci` (survives until
     next retrain, doesn't fix root cause)
   - Wait for upstream Linux kernel changes to add SEC/SLS2-specific
     link policy

2. **The fan control discrepancy is also EC-managed** — Windows uses 6+
   SAM commands for fan control that the Linux kernel doesn't expose.
   The kernel could add these but it'd require:
   - RE of the SmfClient to get the actual command numbers
   - A risk assessment of the side effects (e.g., setting a low SPL
     limit could make the fan spin up under unexpected thermals)

3. **EC FW gap (12.201.139 vs 13.101.139)** — without a release-note
   diff, we can't know if newer EC has different link policy. Could
   be worth checking Microsoft's update tracker.

# Session 2026-08-19 — Phase 2 Live Reconnaissance

## What we did

### 1. SSAM cdev bring-up
- `modprobe surface_aggregator_cdev` → `/dev/surface/aggregator` appeared
  (chardev 10,262). No state change beyond device exposure.

### 2. Live SAM traffic (ftrace, 30s)
Captured to `pcap/ssam-trace.txt`. Source: `tracepoint:surface_aggregator:ssam_ctrl_notif_d0_entry/show`
plus 27 other events. The trace confirmed 4 unique (TC, CID, IID) seen
in real traffic: FAN/0x01/0x01, TMP/0x02/0x00, BAT/0x01/0x01, BAT/0x03/0x01.
All returned status=0.

`upowerd` polls BAT, `nvpl-gui` polls TMP+FAN.

### 3. Static extraction of TC×CID from kernel modules
Far more reliable than blind cdev fuzzing. Two passes over each `.ko`:

- **Pass A** — `movabs $imm64` for packed ssam_request headers
- **Pass B** — `movb` sequences in `ssam_*` functions, reconstructing
  the on-stack struct from consecutive `-0xNN(%rbp)` writes

Result: 23 unique (TC, CID, IID) combinations, 21 of them GET, 2 of them
SET (battery alarm and platform profile). Documented in
`decoded/SAM_TABLE.md` and `decoded/SAM_TABLE.tsv`.

### 4. Validation probe
`TC=0x01 CID=0x13` (SAM firmware version) returns `8b c9 00 0c` →
LE u32 `0x0c00c98b` → (12, 201, 139). `dmesg` independently reports
`SAM firmware version: 12.201.139`. Decode pipeline verified end-to-end.

### 5. Hardware observations
- **EC firmware is 12.201.139**, NOT 13.101.139 from the MSI. This machine's
  EC is one major version behind the package Microsoft is currently
  distributing. Newer EC FW may add/remove SAM commands. Flag for Phase 5.
- `surface_hotplug.ko` contains **zero** `ssam` symbol references →
  confirmed Linux has no SAM path for PCIe/dGPU power gating.
- Baseline unchanged: `platform_profile=balanced`, PCIe Gen 1 x8.

### 6. Discovered platform profile value mapping
By tracing the `cmp/je` ladder in `ssam_platform_profile_set`:

| ACPI name | u32 |
|-----------|-----|
| `low-power` | 1 |
| `balanced` | 2 |
| `balanced-performance` | 3 |
| `performance` | 4 |

Each profile SET also triggers a paired SET to FAN CID 0x0e (IID=1) when
`has_fan` device-property is true.

## What's NOT done (carries forward)

- [ ] **Wide cdev sweep deferred** — instead of a blind 38×32 TC×CID
      enumeration (which would issue ~1200 IOCTLs against an EC we don't
      fully understand, including TCs like 0x09 FWU that could trigger
      firmware update behavior with empty payloads), we extracted the
      known-good table statically. The probe tool is validated and ready
      for a narrow, targeted sweep of specific TCs (PMC=0x04, PoM=0x06)
      if Phase 3 doesn't find the answer in the .sys files.
- [ ] Phase 3: .sys disassembly (focus: `SurfaceAcpiPlatformExtensionDriver.sys`,
      `SurfaceIntegrationDriver.sys`, `SurfaceSmfClient.sys`).
- [ ] ACPI table analysis (DSDT/SSDT decompile for `_DSM` under PCIe objects).
- [ ] Phase 4: EC.md (limited — EC FW encrypted, only cert chain + signer CN
      metadata available statically).
- [ ] Phase 5: `decoded/RECOMMENDATIONS.md`.

## Decision points for the user

1. **Run the narrow cdev sweep anyway?** Even on the safe TCs (PMC, PoM)
   there's nonzero risk — the EC's interpretation of zero-payload queries
   on these TCs is unknown. Recommendation: skip until Phase 3 is complete
   and we know what CIDs to look for.
2. **EC firmware update** (12.201.139 → 13.101.139) — explicitly out of
   scope for this project. Documenting the version gap, not closing it.
3. **Initial git commit** — still pending. The repo is in a clean state.
